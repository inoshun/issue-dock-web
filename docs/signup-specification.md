# サインアップ画面の仕様

## 目的と範囲

新規ユーザーが `/signup` から IssueDock のアカウントを作成できるようにする。画面は日本語で表示する。この文書は画面の振る舞いと受け入れ条件を定める。実装構成と依存ライブラリは [実装設計](signup-implementation.md) に記す。

## 画面

- URL: `/signup`
- タイトル: 「アカウント登録」
- 入力項目: メールアドレス、ユーザー名、パスワード、パスワード確認
- 操作: 「登録する」ボタン。Enter キーによるフォーム送信にも対応する。
- 各入力項目には表示ラベルを付ける。パスワードと確認欄はマスクし、ブラウザーの新規パスワード自動入力に対応する。
- 項目ごとのエラーは該当欄の近くに表示する。送信結果はフォーム内に表示する。

## 入力規則

以下はフロントエンドで適用する規則。文字数は JavaScript の文字列長で判定し、バックエンドも同じ方法を使う。

| 項目 | 規則 |
| --- | --- |
| メールアドレス | 前後の空白を除いて小文字化した後、下記の正規表現に一致すること。必須。 |
| ユーザー名 | 2～100 文字。空白文字を含まないこと。必須。API には `name` として送る。 |
| パスワード | 8～100 文字。英大文字、英小文字、数字、ASCII 記号をそれぞれ 1 文字以上含み、すべての文字が半角の表示可能 ASCII 文字であること。必須。入力値を変換しない。 |
| パスワード確認 | パスワードと完全一致すること。必須。API には送らない。 |

メールアドレスの正規表現は、提供された記述の Markdown エスケープを外し、バックエンドのドメイン規則と照合した次の式を採用する。

```regex
/^(?:[A-Za-z0-9_'+-]+\.)*[A-Za-z0-9_'+-]*[A-Za-z0-9_+-]@(?:[A-Za-z0-9][A-Za-z0-9-]*\.)+[A-Za-z]{2,}$/
```

パスワードには次の **すべて** を適用する。

```regex
/[A-Z]/
/[a-z]/
/[0-9]/
/[!-/:-@[-`{-~]/
/^[\x21-\x7E]+$/
```

ユーザー名の「空白なし」はスペース、タブ、改行などの空白文字を含めない意味とし、`/\s/` に一致する場合はエラーにする。先頭と末尾を暗黙に削除して通過させない。

## 登録操作

1. 「登録する」を押したときに全項目を検証する。無効な場合は API を呼ばず、各エラーを表示し、最初の無効な項目にフォーカスする。
2. 有効な場合は登録処理を 1 回だけ送信する。処理中はボタンを無効化し、連続送信を防ぐ。
3. ブラウザーから `POST {NEXT_PUBLIC_API_BASE_URL}/users` を直接呼ぶ。バックエンドは画面のオリジンを CORS で許可する。
4. 成功時は「登録が完了しました」を表示する。登録後のログインや画面遷移は、行き先の仕様がまだないため含めない。
5. メールアドレス重複時は、その旨を入力者に伝える。入力不正、通信失敗、サーバーエラーでは再確認または再試行できるメッセージを表示する。パスワードやサーバー内部のエラー詳細を表示しない。

## API 契約

| 環境 | API ベース URL | 登録先 |
| --- | --- | --- |
| ローカル | `http://localhost:3000` | `http://localhost:3000/users` |
| 現行の本番 API | `https://issue-dock-api-822574234164.asia-northeast1.run.app` | `https://issue-dock-api-822574234164.asia-northeast1.run.app/users` |
| 独自ドメイン移行後 | `https://api.issue-dock.com` | `https://api.issue-dock.com/users` |

API ベース URL は環境変数 `NEXT_PUBLIC_API_BASE_URL` で設定する。ローカルの API は `http://localhost:3001` からの CORS を許可済み。本番の API は、フロントエンドをデプロイした後に `https://issue-dock.com` を許可元へ追加する。現行の本番 API と独自ドメイン移行後の API のどちらを使用する場合も、この設定が必要。

リクエストは `Content-Type: application/json` を付け、次の形で送る。

```json
{
  "email": "user@example.com",
  "name": "sample_user",
  "password": "Example1!"
}
```

バックエンドの現在の実装では、成功時は本文なしの HTTP 201、入力不正は HTTP 400、登録済みメールアドレスは HTTP 409 を想定する。成功時に JSON 本文があることを前提にしない。想定外の 4xx/5xx と接続失敗も扱う。

## 受け入れ条件

| 操作・入力 | 期待結果 |
| --- | --- |
| `/signup` を開く | タイトル、4 項目、登録ボタンが表示される。 |
| 空欄、形式外のメール、空白を含むユーザー名、条件を満たさないパスワード、確認欄の不一致で送信 | 項目にエラーが表示され、API は呼ばれない。 |
| 有効な値で送信 | `email`、`name`、`password` のみが登録 API に届く。 |
| 送信中に再度ボタンを押す | 重複リクエストが発生しない。 |
| API が 201 を返す | 完了メッセージが表示される。 |
| API が 409 を返す | メールアドレスの重複を伝える。 |
| API が 400、5xx を返すか通信に失敗する | 理由に応じた安全なエラーメッセージを表示し、再試行できる。 |
| ローカル起動 | Web は 3001、API は 3000 で動作し、ブラウザーから登録できる。 |
| 本番からの登録 | `https://issue-dock.com` から API へのリクエストと、その事前確認（OPTIONS）が CORS により許可される。 |

## バックエンドとの差分

隣の `issue-dock-api` の現行実装を確認した結果、画面要件と以下の差がある。画面側では本仕様に従い、API 側も最終的に規則を揃えるのが望ましい。

- API の DTO はメールに `z.email()` を使い、ドメイン層は上記の独自正規表現を使う。境界値によってはフロントエンドを通過しても API が 400 を返す可能性がある。
- API の `name` は前後の空白を除いた長さのみ検証し、途中の空白を禁止していない。画面側は要件どおり、すべての空白文字を禁止する。
- API はパスワード確認値を受け取らないため、一致確認は画面側で行う。

確認元（Web リポジトリのルートからの相対パス）: `../issue-dock-api/src/users/presentation/dto/register-user.dto.ts`、`../issue-dock-api/src/users/presentation/users.controller.ts`、`../issue-dock-api/src/users/domain/value-objects/{email,name,password}.ts`。
